2. NUEVA DECISIÓN: INCORPORAR OCR AHORA
==================================================

Después de analizar las necesidades del portal, decidí que sí quiero incorporar OCR en esta etapa.

OCR es importante porque muchos restaurantes publican sus cartas gastronómicas como fotografías.

Quiero que el sistema pueda detectar estas imágenes, leer los textos que contienen y convertirlos en propuestas de platos y precios.

TECNOLOGÍA PREFERIDA:

Tesseract.js o una alternativa local y gratuita técnicamente mejor justificada.

REQUISITOS:

- Ejecutarse en el navegador del administrador cuando sea viable.
- No requerir una API externa.
- No requerir contratar IA generativa.
- No necesitar instalar Linux.
- No necesitar WSL 2.
- No enviar las fotografías a terceros para el reconocimiento.
- Funcionar desde la aplicación web.
- Poder aprovechar Web Workers para evitar que se congele la interfaz.
- Procesar texto español y números.
- Mantener límites razonables de tamaño, memoria y procesamiento.
- Permitir cancelar un análisis y reintentarlo.

Si Tesseract.js ya está parcialmente instalado o preparado, aprovechá lo existente.

No dupliques bibliotecas ni implementaciones.

3. OCR INTEGRADO CON EL MOTOR UNIVERSAL
==================================================

No quiero que el OCR sea una herramienta desconectada del portal.

Debe formar parte del sistema de importación de información gastronómica.

FLUJO PRINCIPAL:

1. Entro al administrador.

2. Selecciono "Importar desde web".

3. Pego la URL de un restaurante.

4. El motor analiza la página.

5. Extrae la información comercial que encuentra.

6. Detecta fotografías e imágenes disponibles.

7. Intenta identificar cuáles podrían contener cartas gastronómicas.

8. Me permite seleccionar las imágenes que quiero analizar.

9. El OCR reconoce el texto de esas imágenes.

10. El analizador gastronómico intenta identificar:
   - Secciones de la carta.
   - Nombres de platos.
   - Descripciones.
   - Tamaños.
   - Variantes.
   - Precios.
   - Bebidas.
   - Promociones y condiciones.

11. Los resultados aparecen en una pantalla de revisión.

12. Puedo corregir cualquier error.

13. Puedo aceptar, descartar o editar los productos.

14. Los resultados aprobados se incorporan a la ficha correspondiente.

15. La carta queda disponible para publicación.

El OCR debe reutilizar el modelo de cartas, productos, variantes, precios, observaciones y procedencia que ya contempla el proyecto.

No crear un segundo sistema de cartas independiente.

4. EXTRACCIÓN DE FOTOGRAFÍAS
==================================================

La extracción de imágenes desde una web sigue siendo una función PRIORITARIA.

NO debe descartarse.

El motor debe poder detectar, cuando estén disponibles:

- Foto principal del comercio.
- Fotografías del restaurante.
- Fotografías de platos.
- Galerías.
- Imágenes de cartas gastronómicas.
- Imágenes asociadas a productos.

Debe examinar fuentes como:

- Etiquetas img.
- Atributos src y srcset.
- Imágenes de carga diferida.
- Metadatos OpenGraph.
- Datos estructurados.
- Enlaces públicos a imágenes.
- Galerías presentes en el HTML.
- Otros mecanismos razonables compatibles.

No prometer acceso a fotografías que estén protegidas, requieran autenticación o dependan de mecanismos todavía no implementados.

IMPORTANTE:

Extraer o detectar una fotografía NO equivale a tener autorización para republicarla.

Respetar el sistema de permisos y derechos que ya contempla el proyecto.

El OCR puede analizar material obtenido legítimamente, pero ninguna fotografía externa debe publicarse sin contar con una base de uso válida.

El reconocimiento no debe exigir publicar ni conservar permanentemente la fotografía original.

5. IDENTIFICACIÓN DE CARTAS FOTOGRAFIADAS
==================================================

Quiero que el motor intente diferenciar entre:

A. Una fotografía de comida.

B. Una fotografía del establecimiento.

C. Una imagen que probablemente contiene una carta o lista de precios.

Para ello puede utilizar señales como:

- Nombre del archivo.
- Texto alternativo.
- Página donde aparece.
- Texto cercano.
- Palabras como carta, menú, precios, comidas o bebidas.
- Características del contenido reconocidas mediante OCR.

No es necesario analizar automáticamente todas las fotografías de cada web.

Priorizá las imágenes con mayor probabilidad de contener información gastronómica escrita.

Si el sistema no está seguro, debe permitir que yo seleccione manualmente la imagen que quiero analizar.

Evitá descargar y procesar decenas de fotografías innecesariamente.

6. RECONOCIMIENTO DE PRODUCTOS Y PRECIOS
==================================================

Después del OCR, el texto debe pasar por el analizador de cartas del motor.

Ejemplo ilustrativo:

MUZZARELLA
Individual $9.000
Grande $14.000

NAPOLITANA
Individual $11.000
Grande $16.000

El resultado esperado es:

Producto: Muzzarella
Variante: Individual
Precio: 9000 ARS

Producto: Muzzarella
Variante: Grande
Precio: 14000 ARS

Producto: Napolitana
Variante: Individual
Precio: 11000 ARS

Producto: Napolitana
Variante: Grande
Precio: 16000 ARS

El ejemplo es ficticio y solo ilustra el comportamiento.

REQUISITOS:

- Reconocer precios argentinos.
- Interpretar puntos y comas correctamente.
- Distinguir tamaños.
- No mezclar productos.
- No asignar un precio al plato equivocado.
- Conservar el texto original.
- Registrar de qué imagen proviene cada resultado.
- Registrar los datos dudosos.
- No inventar nombres ni precios ilegibles.
- Permitir corregir todo desde la interfaz.
- Nunca publicar resultados automáticamente sin aprobación.

Si no puede reconocer una parte de la carta, debe decirlo claramente.

10. SEGURIDAD
==================================================

El contenido obtenido desde Internet debe tratarse como no confiable.

El OCR no debe introducir nuevos riesgos innecesarios.

REQUISITOS:

- No ejecutar scripts extraídos de las páginas.
- No insertar HTML externo directamente en nuestra interfaz.
- Mantener las protecciones SSRF del proxy.
- Validar URLs y redirecciones.
- Validar el tipo real de las imágenes.
- Limitar el tamaño de los archivos.
- Evitar consumo excesivo de memoria.
- Mostrar texto reconocido de manera segura.
- No guardar datos externos como instrucciones ejecutables.
- No permitir que los resultados de OCR eviten la revisión editorial.
- Mantener permisos y roles de administración.
- No abrir la importación general al público antes de completar los controles de seguridad necesarios.

Utilizar recursos de OCR cargados desde dependencias y archivos controlados por nuestra aplicación, no scripts arbitrarios de sitios analizados.

No confundir procesamiento de imágenes con ejecución de JavaScript externo.
